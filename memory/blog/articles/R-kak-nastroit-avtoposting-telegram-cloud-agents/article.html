Автопостинг в Telegram через Cloud Agents Cursor настраивается так: форк репозитория rss-ai-telegram, токен бота только в секретах кабинета Cursor, пробный прогон без отправки в канал, затем один живой пост из RSS в тестовый чат. Боль знакома – ручной копипаст новостей каждый день. Результат вечера: пост сам, без календаря отложки и без сценария Make в первый час.

Когда Cloud Agent с RSS не подходит

Не берите этот путь, если посты нужно писать вручную под tone of voice бренда и ставить точное время в календарь – тут ближе обычная отложка. Не стартуйте с основного канала: ошибка chat_id или дубль state сразу увидит аудитория. Не ждите десять постов за один цикл: шаблон сознательно режет до одной ссылки.

Если нужен мультипостинг без репозитория, соседний маршрут – Make. Если нужен разбор режимов Cursor целиком – смотрите гайд по Cloud Agents и сравнение Automations/SDK. Сегодняшняя цель узкая: один RSS → один тестовый пост → state в remote.

Суть простыми словами: Cloud Agent читает RSS и кладёт один пост в Telegram, пока ноутбук закрыт. Это не SMMplanner и не ControllеrBot. Внешние ключи LLM шаблону не нужны – хватает Bot API, фидов и файла уже отправленных ссылок. Ориентир на вечер: dry-run → один живой пост → TSV в remote без дубля.

Обновлено: 25.07.2026

ControllеrBot и SMMplanner ждут, что вы сами напишете текст и поставите время. Здесь другая задача: программа в облаке Cursor сама читает ленту новостей сайта и кладёт один пост, пока ноутбук закрыт. Внешние ключи к нейросетям шаблону не нужны – достаточно Telegram Bot API, встроенного RSS и списка уже отправленных ссылок.

Чем Cloud Agent отличается от отложки

Отложка – вы сами готовите черновик. Cloud Agent – программа в облаке Cursor, которая запускается по кнопке Test run или позже по расписанию. Automations в Cursor – это таймер и триггеры поверх такого агента. Make остаётся нормальным соседним путём, если нужен мультипостинг в Telegram и VK без кода; для первого вечера я бы не смешивал оба стека.

Схема на вечер:
BotFather + chat_id → форк rss-ai-telegram → Secrets → dry-run → один живой пост → проверка TSV → только потом cron

  1. Создайте бота в @BotFather и сохраните TELEGRAM_BOT_TOKEN вне чатов.
  2. Добавьте бота админом тестового чата и узнайте TELEGRAM_CHAT_ID.
  3. Форкните Horosheff/rss-ai-telegram и при необходимости поправьте RSS_FEEDS.
  4. Подключите форк к Cloud Agents и положите токен в Dashboard Secrets.
  5. Запустите pip install -r requirements.txt && ./scripts/run_once.sh с PIPELINE_DRY_RUN=true.
  6. Уберите dry-run, сделайте один боевой Test run и проверьте пост в Telegram.
  7. Убедитесь, что state/posted_news.tsv ушёл в remote, затем повторите run без дубля.

Итоговый вердикт: для первого вечера с RSS берите форк и Cloud Agent. Make оставляйте на мультиплощадки. Не смешивайте оба стека в один час.

Шаблон из репозитория за один цикл публикует максимум одну новую ссылку. Это не "залить канал лентой". Повторный запуск не должен слать тот же URL: состояние хранится в SQLite и в файле state/posted_news.tsv, а после успешной отправки скрипт коммитит и пушит TSV. Раньше без такого state облачное расписание дублировало новости – это закрыли в issue #6 репозитория.

Нужен платный план Cursor: без него Cloud Agents не стартуют. Секреты кладут во вкладку Dashboard → Cloud Agents → Secrets, а не в README и не в git.

Бот, chat_id и тестовый канал

В Telegram откройте @BotFather, команда /newbot. Сохраните TELEGRAM_BOT_TOKEN вне чатов и вне репозитория. Добавьте бота администратором тестового канала или чата с правом публиковать сообщения. Без админки сценарий может быть "зелёным", а пост не появится.

TELEGRAM_CHAT_ID узнайте через GetMyID или getUpdates. У каналов идентификатор часто выглядит как -100… – минус в начале важен. Для первого боевого прогона я бы брал отдельный тестовый чат, а не основной канал с аудиторией.

Лимит Bot API на текст sendMessage – от 1 до 4096 символов, поддерживается HTML-разметка. Если пост обрежется или разметка "поедет", смотрите длину текста и теги, а не "магию агента".

Форк, Secrets и команда запуска

Форкните github.com/Horosheff/rss-ai-telegram, ветка main. Откройте news_bot/config.py и при необходимости замените RSS_FEEDS на ленты своей ниши: отраслевые сайты, блоги вендоров, пресс-релизы. Если оставить чужие фиды "как в демо", в канал уедут не ваши новости – это не баг агента, а неверный список источников.

Подключите форк к Cloud Agents в Cursor. В Secrets добавьте TELEGRAM_BOT_TOKEN и при необходимости TELEGRAM_CHAT_ID. В env.example репозитория те же имена переменных плюс пути к базе и к posted_news – ориентир, что именно агент ждёт из окружения. Токен в коде, в issue или в чате "на пять минут" – плохая идея: его потом сложно отозвать из всех копий.

Канон команды из README репозитория:

pip install -r requirements.txt && ./scripts/run_once.sh

Именно её ставьте в Test run агента. Окружение подтянет секреты как переменные среды; если агент пишет, что secrets aren’t available, откройте cursor.com/dashboard/cloud-agents и проверьте Secrets там, а не файлы в git.

Сначала dry-run, потом один живой пост

Поставьте PIPELINE_DRY_RUN=true в Secrets или в переменных запуска. Dry-run (пробный прогон) собирает текст кандидата, но не отправляет сообщение в Telegram и не пишет запись в базу. Смотрите JSON-статус в логе: есть кандидат из RSS, нет ошибки парсинга, chat_id на месте. Если кандидата нет – проверьте, что фиды отдают свежие URL и что список в config.py не пустой.

Уберите dry-run (PIPELINE_DRY_RUN=false или удалите флаг) и запустите боевой Test run. Критерий "получилось": в тестовом чате или канале виден один новый пост из RSS. Откройте репозиторий на GitHub и проверьте, что state/posted_news.tsv обновился и ушёл в remote – иначе следующий cron снова не будет помнить отправленные URL. Пока TSV не в remote, облачный запуск на чистой машине каждый раз "забывает" историю.

Сразу сделайте второй ручной запуск на том же репозитории. Ожидайте либо нового кандидата, либо статус вроде all_duplicates – но не второй такой же ссылки. Если дубль пришёл, почти всегда виноват непопушенный state или второй chat_id, а не "Telegram сам захотел".

Расписание – только после ручной проверки

Automation с cron имеет смысл, когда ручной Test run на том же репозитории уже дал пост без дубля. В настройках Automations для code-репо явно укажите repository: cron по умолчанию может оказаться без репозитория, и агент будет крутиться впустую.

Я бы не ставил расписание в тот же час, когда только получили токен. Сначала два ручных прогона: dry-run и боевой. Потом таймер.

Что не тащить в тот же вечер

Не ставьте рядом рой субагентов, Офис, Hyperion или полный автоблог Excalibur – это другой уровень сложности. Не ищите "ТОП-10 ботов автопостинга" как замену Secrets и dry-run. Не обещайте себе ленту из десяти постов за один цикл: шаблон сознательно режет до одной публикации за запуск.

Частые вопросы

Нужны ли ключи OpenAI или другого LLM?

Нет. Репозиторий rss-ai-telegram рассчитан на TELEGRAM_BOT_TOKEN и при необходимости TELEGRAM_CHAT_ID. Внешние LLM API для первого вечера не обязательны.

Почему бот молчит, хотя лог без ошибки?

Чаще всего бот не админ канала или неверен chat_id. Проверьте право публиковать и формат -100… для каналов.

Можно ли сразу лить в основной канал?

Технически да, практично – нет. Сначала тестовый чат, dry-run, один боевой пост, проверка, что повторный run не дублирует URL. Потом тот же Secrets и тот же репозиторий на боевой chat_id.

Чем это лучше ControllеrBot и SMMplanner?

Тем, что вам не нужна пачка подписок на отложку, если цель – агент, который сам тянет RSS. Если цель – вручную писать посты и ставить время, SaaS-календарь может быть уместнее. Для "новости сами, пока я занят" я бы начинал с форка и Cloud Agent.

Нужен ли платный план Cursor?

Да для Cloud Agents. Без платного плана агент в облаке не стартует. Секреты всё равно кладите в Dashboard, даже на платном тарифе.

Что делать, если повторный run шлёт тот же URL?

Проверьте, что state/posted_news.tsv закоммичен и запушен. Облачный запуск на чистой машине без remote-state каждый раз забывает историю.
