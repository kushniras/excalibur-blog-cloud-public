Чтобы сделать вебхук, который будит агента Cursor на заявку, создайте Automation с триггером Webhook – это входящий HTTP-адрес: на него приходит POST, и агент стартует сам. Сохраните URL, отправьте тестовый POST и дождитесь артефакта. Боль знакома: вручную открывать чат на каждую форму. Результат вечера: заявка будит агента без вашего клика в IDE сегодня.

Когда webhook Automation не нужен

Если задача разовая – ответить на один вопрос в чате – хватит обычного Agent. Если нужен тик по времени без внешнего события – берите расписание, не webhook. Если нет понятного payload от формы или Make, сначала соберите минимальный JSON, иначе агент будет стартовать "в пустоту".

Не путайте URL Automation с webhooks Cloud Agents API из другой документации: смотрите тот экран, где создаёте Automation. Успех вечера – один тестовый POST и один наблюдаемый результат агента, не зоопарк интеграций.

Webhook Automation – не то же самое, что Discord-бот, Make сам по себе или cron. Сначала один URL и один тестовый POST. GitHub нужен, если агент пишет в репозиторий; пустой URL на этапе настройки – ещё не готово. Make может слать POST на этот адрес после формы.

В поиске по "как сделать вебхук" чаще выпадают Discord и Битрикс. Вам нужен другой результат: событие с формы или CRM стучится в Cursor, а агент сам пишет бриф или ответ клиенту – без ручного открытия чата. Репозиторий GitHub для этого прогона не нужен.

Чем это отличается от Discord, Make и расписания

В Cursor Automations триггер Webhook создаёт закрытый endpoint: после Save появляются URL и API key, запрос – HTTP POST на этот адрес. Официально так и описано в документации Cursor.

Триггер Как будит агента Когда нужен
Webhook Automation Входящий HTTP POST на URL Cursor Заявка с формы / Make / CRM
Schedule / cron Таймер по расписанию Регулярный отчёт, не событие
Make HTTP Сценарий шлёт POST на webhook Связка форм и таблиц без кода
Ручной чат Agent Вы пишете промпт сами Разовый разбор, не поток заявок

Итоговый вердикт: для ответа на заявку без ручного чата берите Webhook Automation. Расписание – другой сценарий, не подменяйте одно другим.

Коротко по развилке, чтобы не смешать соседние задачи:

  • Cursor Automations + Webhook – событие будит думающего агента, который читает поля заявки и пишет текст.
  • Расписание (Scheduled) – запуск по времени, не по заявке. Если позже понадобится cron, это отдельный гайд про Automations по расписанию.
  • Make Custom Webhook – сценарий Make принимает данные и гоняет модули. Полезно, но это не "агент Cursor ответил на JSON". См. первый сценарий Make с вебхуком.
  • Cloud Agents API status webhooks – исходящие уведомления о статусе агента (ERROR/FINISHED) с HMAC. Другой контур: Cursor сообщает наружу, а не принимает вашу заявку как триггер.

Я бы начинал именно с входящего Webhook в Automations. Один адрес, один промпт, один тестовый POST – этого достаточно, чтобы проверить пользу.

Что подготовить до кликов

Нужен аккаунт Cursor с доступом к Cloud Agents / Automations и способ отправить один HTTP POST: curl, Postman или HTTP-модуль в Make. Репозиторий подключать не обязательно: для текстового брифа подходит режим без репозитория – агент не клонирует код и не открывает pull request.

Интерфейс Automations открывается по пути cursor.com/automations в браузере или через Agents Window в продукте. Ссылку на этот UI в статье не кликаю намеренно: у ботов и части CDN он отдаёт 403. Рабочие страницы с описанием – в документации Automations и help Cursor.

Помните про оплату: Automations считаются как использование cloud agent; в обзорах Learn Cursor отмечают, что они идут в Max Mode – режиме полной мощности модели. Для первого теста это нормально, но не гоняйте десяток пустых POST "на всякий случай".

Создаём Automation с триггером Webhook

Откройте Automations → New Automation. В триггерах выберите Webhook. Можно добавить несколько триггеров позже; сегодня достаточно одного.

Промпт держите узким. Пример смысла, не дословный шаблон канала:

В конце сообщения будет JSON заявки. Прочитай поля name, service и question. Составь короткий бриф для менеджера: кто написал, какая услуга, в чём вопрос, что ответить первым сообщением. Код не правь, репозиторий не трогай, ответь только текстом.

Repository: No repository – без репозитория. Так вы снимаете страх "сломаю код": агент работает с текстом события. Tools вроде Memories для недоверенного ввода с формы на первом прогоне лучше не включать без нужды.

Сохраните и активируйте Automation. Только после Save появляются webhook URL и API key. До сохранения адрес "пустой" – это не баг, так устроен продукт. Ключ никуда не публикуйте: ни в общий чат, ни в скриншот для Telegram.

Тестовый POST: что отправить и что считать успехом

Отправьте POST на скопированный URL. В заголовке укажите авторизацию Bearer с API key. В теле – простой JSON, как от формы: {"name":"Анна","service":"консультация","question":"Сколько длится созвон и что подготовить?"}.

Важный факт из форума Cursor (сотрудник Colin, 9 марта 2026): тело webhook передаётся as-is в конец промпта Automation. Отдельный парсер формата не нужен. Часть людей получала от email-поддержки обратное мнение – пока сами не посмотрели историю прогонов. Ориентируйтесь на то, что видно в history после вашего POST.

Критерий "получилось" простой:

  1. Automation сохранена с триггером Webhook;
  2. после Save видны URL и API key;
  3. в history есть успешный прогон именно от тестового POST;
  4. в ответе агента узнаются поля заявки – имя, услуга, вопрос.

Если прогона нет – проверьте, что Automation активна, URL скопирован целиком, в заголовке именно Bearer-ключ этой автоматизации, метод POST, а не GET. Если ключ "умер" после смены прав на Team Owned – по документации нужно заново сгенерировать webhook API key; старый перестанет подходить.

Типичные ошибки вечера

Самая частая путаница – принять любой "вебхук из выдачи" за путь к агенту Cursor. Discord шлёт сообщения в канал, Битрикс крутится вокруг CRM, Make пишет в сценарий, исходящий status-webhook Cloud Agents API сообщает, что агент закончил работу. Сегодня нужен входящий endpoint Automations.

Вторая ошибка – подключить репозиторий "на вырост": для брифа по заявке это лишний риск. Третья – повесить сразу schedule и webhook на одну задачу: несколько триггеров продукт допускает, но вечером мешает понять, что разбудило агента.

Не обещайте себе "агент 24/7 без вас" после одного клика Save. Без тестового POST и проверки history у вас есть только форма в UI. Сначала один чистый прогон, потом подключайте реальную форму, Tilda или HTTP-модуль Make как отправителя того же POST – не как новую тему вечера.

Частые вопросы

Нужен ли GitHub, чтобы вебхук заработал?

Нет. Для текстового ответа на заявку достаточно No repository. Репозиторий понадобится, когда агент должен править код или открывать PR – это уже другая задача.

Почему URL пустой, пока я настраиваю форму?

Потому что endpoint появляется после Save. Сначала сохраните и активируйте Automation, потом копируйте URL и ключ.

Можно ли слать POST из Make?

Да, как из любого HTTP-клиента: URL Automations + Bearer + JSON. Это опциональный отправитель. Не путайте с Make Custom Webhook как главной целью вечера – сегодня цель в history Cursor, а не в модулях сценария.

Это то же самое, что webhooks в Cloud Agents API?

Нет. API webhooks – исходящие statusChange с подписью HMAC. Automations Webhook – входящий POST, который будит агента по вашему событию.

Что считать успехом тестового POST?

URL Automation сохранён, тестовый POST вернул ожидаемый статус, агент стартовал и оставил артефакт или лог. Пустой URL на этапе настройки – ещё не готово.

Нужно ли сразу подключать Discord и CRM?

Нет. Сначала один webhook и один понятный payload. Discord, CRM и цепочки Make добавляйте после ручного успеха.
